# PyRIT：怎样组织多轮与变化输入的风险测试

攻击不一定在一次提问中完成。对话历史、语言变化和重复尝试可能逐步改变系统行为，单轮测试难以观察这一过程。**PyRIT 组织变化输入与多轮会话，并记录目标响应和评分状态。** 要解释结果，需要预先固定允许行为、查询预算及会话级成功条件。

## 输入变换与多轮执行的组织方式

[技术解释] PyRIT 是生成式 AI 风险识别框架。目标适配器连接被测系统，输入转换器产生变体，攻击执行与评分器记录会话及判定。项目从 Azure 迁至 microsoft 仓库。1.1.0 版本包含多语言、输入变换等扩展，并显式支持无法确定的评分状态。

数据流：测试目标与攻击输入 → 变换／多轮执行 → 目标响应 → 评分 → 会话记录。目标模型、攻击模型、评分模型可能是不同服务，均需分别确认数据去向和成本；完整对话记忆可能含提示与秘密测试标记。

## 从固定输入扩展到受控会话测试

假设合成目标不得披露秘密标记。一次会话可以先询问普通资料，再通过改写、编码或语言变化尝试提取该标记。测试需要记录每轮实际发送的内容和目标响应，并说明以哪种可观察结果判定泄露。仅出现相似词语，与完整标记被输出或经工具传送，是不同的成功条件。

先用固定输入确认目标接入和评分逻辑，再引入变体，能够避免将接口故障误认为稳健防御。不同会话之间应恢复到约定的初始状态；同一会话内则保留需要测试的历史。否则上一案例留下的记忆会改变下一案例的前提，最终比例难以复核。

[参考方法] 从只含合成内容的测试目标开始，定义要观察的失效、轮数和查询预算。先运行单轮固定输入确认接入及评分，再加入多轮、编码或语言变体。记录终止原因、原始响应与评分状态；重置会话以避免记忆污染不同测试。

按已核实 release 的官方 notebooks 学习 API。攻击成功后缩减到可复现的最小输入，人工核对是否真的突破应用边界。评分不确定、请求错误及预算耗尽应独立列出，不合并为成功防御。

## 按会话状态解释成功比例

[教学示例] 下表是 30 个合成会话的分类，不能把请求错误或评分不确定默认为成功或失败：

<div class="tool-evidence-table" markdown="1">

| 会话状态 | 数量 | 计入确定样本成功率？ |
|---|---:|---|
| 确认攻击成功 | 3 | 是，计入分子 |
| 确认未成功 | 24 | 是，计入分母 |
| 请求错误 | 2 | 否，无法判断完整测试结果 |
| 评分不确定 | 1 | 否，须人工复核或重测 |
| 合计 | 30 | — |

</div>

只在 27 个确定分类的会话中计算，结果为 `3 / (3 + 24) ≈ 11.1%`。另一个口径 `3 / 30 = 10%` 表示“已确认成功会话占全部发起会话的比例”；它没有把 3 个未决会话确认成失败，不能直接称为通常意义上的成功率。报告时应同时列出 2 个请求错误和 1 个不确定评分。

多轮攻击每个会话可产生多个请求，因此请求命中率和会话成功率不同；较高查询预算也会增加发现机会，不能直接比较不同预算的工具分数。

## 测试预算和攻击分布限定结果范围

测试覆盖不等于真实攻击分布，裁判可能漏判或被响应误导。框架不能自动定义业务边界或证明整体安全。替代选择：[garak](garak.md) 的探针扫描、[Promptfoo](promptfoo.md) 的插件与攻击策略，或人工多轮合成挑战。工具选择按目标接口、复现要求和覆盖能力，避免无依据的优劣排名。
